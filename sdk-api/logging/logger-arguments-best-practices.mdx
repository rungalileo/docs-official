# Understanding Logger Arguments

This guide helps you understand the different arguments available to you within the Galileo Logger and how to best use them.

When working with the Galileo Logger, understanding how to effectively use the various arguments available can significantly enhance your ability to monitor, debug, and optimize your AI applications. This guide will walk you through each argument, explain its purpose, and provide best practices for using them effectively.

## About the Galileo Logger

The Galileo Logger provides several arguments that allow you to capture rich context about your AI operations. These arguments serve different purposes and should be used strategically to create comprehensive observability into your application's behavior.

### Core arguments overview

Before diving into best practices, let's understand what each argument does:

- **`input`** - The primary data being processed by your AI operation
- **`redacted_input`** - A sanitized version of input for sensitive data handling
- **`name`** - A human-readable identifier for your trace or span
- **`duration_ns`** - Performance timing in nanoseconds
- **`created_at`** - Timestamp for when the operation began
- **`metadata`** - Key-value pairs for additional context
- **`external_id`** - Integration point for external systems

## Detailed argument guide

### 1. Input Argument

**Purpose**: The `input` argument captures the primary data that your AI operation processes. This is the foundation of your observability strategy.

**Why This Matters**: Clear, structured input helps you:

- Debug issues by understanding the exact data that caused problems
- Analyze patterns in user queries or system inputs
- Train better models with high-quality input data

### 2. Redacted input Argument

**Purpose**: The `redacted_input` argument provides a sanitized version of your input data, removing sensitive information while maintaining the structure needed for analysis.

#### Best practices:

<SnippetRedactedInputArgument />

**Why this matters**: Redacted input helps you:
- Comply with data privacy regulations (GDPR, CCPA, etc.)
- Share logs with team members without exposing sensitive data
- Debug issues in production without compromising security
- Maintain data quality for analysis while protecting user privacy

### 3. Name argument

**Purpose**: The `name` argument provides a human-readable identifier that makes it easy to understand what each trace or span represents.

#### Best practices:

<SnippetNameArgument />

**Naming conventions**:

- **Use action verbs**: "Generate Response", "Retrieve Documents", "Validate Input"
- **Include context**: "Medical Diagnosis Query", "Payment Processing", "User Authentication"
- **Be specific**: "GPT-4 Response Generation" vs "LLM Call"
- **Use consistent patterns**: "Service - Action - Context" format

**Why This Matters**: 
Good naming helps you:
- Quickly identify the purpose of each operation in logs
- Filter and group related operations effectively
- Debug issues by understanding the workflow context
- Create meaningful dashboards and alerts

### 4. Duration argument

**Purpose**: The `duration_ns` argument captures performance timing in nanoseconds, enabling detailed performance analysis.

#### Best practices:

<SnippetDurationArgument />

**Why This Matters**: Accurate timing helps you:
- Identify performance bottlenecks in your AI pipeline
- Set appropriate timeouts and SLAs
- Optimize resource allocation
- Monitor system health and degradation

### 5. Created at (created_at) argument

**Purpose**: The `created_at` argument captures when an operation began, enabling temporal analysis and debugging.

#### Best practices:

<SnippetCreatedAtArgument />

**Why This Matters**: Proper timestamp handling helps you:
- Debug issues by understanding when they occurred
- Analyze temporal patterns in your application
- Correlate events across different systems
- Maintain audit trails for compliance

### 6. Metadata argument

**Purpose**: The `metadata` argument allows you to attach key-value pairs that provide additional context about your operations.

#### Best practices:

<SnippetMetadataArgument />

#### Metadata best practices:

- **Be consistent**: Use the same keys across similar operations
- **Include version information**: Model versions, API versions, client versions
- **Add operational context**: Environment, user context, session information
- **Keep it relevant**: Don't add metadata that doesn't help with debugging or analysis
- **Use appropriate data types**: Strings for most values, numbers for metrics

**Why this matters**: Rich metadata helps you:
- Debug issues by understanding the full context of operations
- Analyze performance across different configurations
- Track user behavior and preferences
- Maintain operational visibility across complex systems

### 7. External ID argument

**Purpose**: The `external_id` argument provides a bridge between Galileo and external systems, enabling correlation and integration.

#### Best practices:

<SnippetExternalIdArgument />

#### External ID best practices:

- **Use consistent prefixes**: `payment_`, `request_`, `ticket_`, `order_`
- **Include the actual ID**: Make it easy to look up in external systems
- **Keep it unique**: Ensure each external ID is unique within your system
- **Make it searchable**: Use formats that work well with your external systems

**Why This Matters**: External IDs help you:
- Correlate Galileo data with external monitoring systems
- Link AI operations to business processes
- Debug issues across multiple systems
- Maintain audit trails for compliance and security

## Best Practices Summary

### Do's ✅

1. **Use descriptive names** that clearly indicate the operation's purpose
2. **Structure your metadata** consistently across similar operations
3. **Implement proper redaction** for sensitive data
4. **Include version information** in metadata for debugging
5. **Measure timing accurately** for performance analysis
6. **Use external IDs** to correlate with other systems
7. **Be consistent** with naming conventions and data formats

### Don'ts ❌

1. **Don't log sensitive data** without proper redaction
2. **Don't use generic names** like "Query" or "Process"
3. **Don't overload metadata** with irrelevant information
4. **Don't skip timing measurements** for performance-critical operations
5. **Don't forget to include context** that helps with debugging
6. **Don't use string timestamps** instead of proper datetime objects
