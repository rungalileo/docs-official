Before you rely on a custom metric to measure your agentic system's performance, test it to confirm it scores the way you intend. Galileo gives you three ways to test, from a quick sanity check to a quantitative measure of how closely the metric matches your ground truth.

## Choose how to test

| Method           | Best for                                                                              |
| :--------------- | :------------------------------------------------------------------------------------ |
| **Manual input** | A quick check of a single input/output pair as you draft the prompt.                  |
| **Current Logs** | Seeing how the metric behaves on your most recent real sessions, traces, or spans.    |
| **Datasets**     | Measuring how closely the metric matches known-correct answers, with a macro F1 score or RMSE. |

You'll find all three on the **Test Metric** tab when creating or editing a metric.

## Test with manual input

Provide an input and output and select **Test**. You'll see the metric result, plus an explanation if step-by-step reasoning is turned on.

![A manual metric test showing a fail score and an explanation](/concepts/metrics/custom-metrics/test-metric-manual.webp)

Due to the complex structure of sessions and traces, manual input is only supported for metrics that apply to **spans**.

## Test against current logs

Select the project, choose the source type, then pick a Log Stream or Experiment. Select **Test Metric** to run the metric against your last 5 logged sessions, traces, or spans. Select any row to see the explanation.

![A test run against 5 Log Stream rows showing they all pass with 100%](/concepts/metrics/custom-metrics/test-metric-logs.webp)

This is the fastest way to see how a metric behaves on real, representative data.

## Test against a labeled dataset

Manual and log-based tests confirm a metric *runs* correctly. To know how much you can *trust* it, test it against a labeled dataset—one with a **Metric Ground Truth** column holding the correct result for each row. Galileo runs the metric across the dataset and reports a single score for how well the metric's output matches your Metric Ground Truth: a **macro F1 score** for label-based metrics, or **RMSE** for number-based metrics.

<Note>
  Dataset testing is available for metrics that apply to a **trace or LLM span**, where you can provide Metric Ground Truth per row. Session-level metrics aren't supported.
</Note>

## Why test against a dataset

Testing against a labeled dataset does more than confirm a metric runs—it gives you a quantitative signal you can act on and return to. The workflows below use the macro F1 score for label-based metrics; for number-based metrics, the same applies using RMSE.

### Validate your metric prompt

Before you deploy a metric to a Log Stream, dataset testing tells you whether the prompt is actually scoring the way you intended. A high macro F1 score against a *representative* set of labeled examples is a meaningful signal that the metric will score consistently on similar data in production.

### Establish a baseline

Run a dataset test when you first create a metric and record its macro F1 score. That becomes your baseline. Re-run the **same dataset test** after any future change—a prompt edit, a different model, a new number of judges—to tell whether it helped or hurt, since the comparison is only meaningful against the same labeled set.

### Validate improvements quantitatively

When you iterate on a metric prompt, re-running the same dataset test shows whether the change actually improved how the metric scores, rather than just shifting its behavior on a handful of examples. This is especially useful with [Autotune](/concepts/metrics/autotune-llm-as-a-judge-metrics): test before and after an Autotune run on a set of held-out labeled examples—ones you didn't give Autotune as feedback—so a higher macro F1 score reflects a real improvement and not overfitting to the feedback.

### Detect evaluation drift

Metric behavior can drift when underlying models change. Re-running the same dataset test after a model upgrade or API change gives you a concrete comparison: if the macro F1 score drops, you know the metric needs attention before it affects your evaluations.

## Run a dataset test

<Steps>
  <Step title="Add a dataset">
    On the **Test Metric** tab, select **Datasets**, then choose an existing dataset or upload one with your inputs and outputs.
  </Step>

  <Step title="Add Metric Ground Truth">
    For each row, provide the expected result in the **Metric Ground Truth** column—the value the metric should return when it scores correctly. A single dataset can hold ground truth for several metrics at once, stored separately and keyed by metric name, so you can reuse one dataset across your metric library.
  </Step>

  <Step title="Run the test">
    Run the metric across the dataset. Galileo scores every row and compares the output against your Metric Ground Truth.
  </Step>

  <Step title="Review the score">
    Once the run completes, Galileo reports a single aggregate score: a **macro F1 score** (0–1, higher is better) for boolean, categorical, or multi-label metrics, or **RMSE** (lower is better) for count, discrete, or percentage metrics. Use this score to decide whether the metric is ready to deploy or needs further iteration.
  </Step>
</Steps>

## How scores are calculated

Galileo compares the metric's output against the Metric Ground Truth for every labeled row, then reports a single score that fits the metric's output type.

### Label-based metrics: macro F1

For metrics that return a label—boolean (true/false), categorical (named classes), or multi-label—Galileo reports a **macro F1 score**: a single number from 0 to 1 for how well the metric's labels match your Metric Ground Truth.

F1 combines two things:

- **Precision** — of the rows the metric flagged, how many were correct. False positives (flagging something it shouldn't) lower precision.
- **Recall** — of the rows that should have been flagged, how many the metric caught. False negatives (missing something it should have) lower recall.

F1 is the balance of the two, so a metric only scores well when it keeps both false positives and false negatives low. The **macro** F1 averages this across every label, so each label counts equally and a metric can't score well just by getting the most common case right.

The goal is a **high** macro F1 score, not a perfect one—perfect alignment is rarely achievable with subjective judgments. Iterate on the prompt, model, or number of judges and re-test until it's high enough for your use case.

### Number-based metrics: RMSE

For metrics that return a number—count, discrete, or percentage—a macro F1 score doesn't apply. Galileo reports **RMSE (root mean squared error)**: how far the metric's values are from your Metric Ground Truth on average. Lower is better, and 0 means an exact match.

### Score by output type

| Output type                 | Score    | Reading it                        |
| :-------------------------- | :------- | :-------------------------------- |
| Boolean, Categorical, Multi-label | Macro F1 | 0–1, higher is better        |
| Count, Discrete, Percentage | RMSE     | Lower is better (0 = exact match) |
